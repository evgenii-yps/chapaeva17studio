# Этап 4. Сцена, персонаж, рендер (scene3d)

## Что сделано
- `work/scene/build_scene.py` — из BVH строит сцену и рендерит видео персонажа **без звука** (PNG-серия в `work/scene/_tmp_frames/` -> ffmpeg libx264, yuv420p, crf 18, `-an`). Возобновляемо: готовые PNG пропускаются.
- Персонаж-манекен строится процедурно **по длинам костей импортированной арматуры** (суставные шары + сужающиеся капсулы, глянцевые «сглаженные» нормали): молочно-белый костюм, бежевые голова/кисти, тёмная «шапочка» волос (подсказывает, куда смотрит манекен), светлая обувь, шалфейный пояс. Привязка жёсткая: одна вершинная группа на кость + Armature-модификатор, шары на суставах закрывают сгибы (разрывов нет). Работает и для T-позы (реальный BVH), и для A-позы (тестовый BVH).
- Студия: светлая комната, деревянный пол с рисунком досок (Brick + растянутый шум, процедурно), светлые стены, плинтус, реечная панель из дерева на задней стене, окно с импостами в левой стене (светящаяся «небесная» плоскость + area-свет), заполняющий area-свет, мягкий светлый World. Вся статическая геометрия склеена по материалам (мало draw call).
- Камера: 3/4, азимут 35 градусов от фронтального вида (камера на мировой +X, то есть со стороны левой руки персонажа), фокус 50 мм (экв. 35 мм), высота 1.25 м, **горизонтальный взгляд (pitch=0, вертикали не заваливаются), кадрирование — lens shift**. Рамка подбирается автоматически по ВСЕМУ движению (все суставы, каждый ~5-й кадр), запас 10 %, + плавное следование за тазом вдоль «правого» вектора камеры (доля 0.7, гауссово сглаживание ~1.2 с). `--follow 0` — полностью фиксированная камера. Для реального BVH камера в ~5.1 м от центра рамки.
- Тени: режим `--quality fast` (по умолчанию): без теневых карт EEVEE + мягкие тёмные «пятна-тени» на полу под тазом и стопами (Copy Location на кости, только X/Y) — почти бесплатно. `--quality balanced`: настоящие тени EEVEE.
- `work/scene/pilot.blend` (0.9 МБ) — собранная сцена с реальным BVH (камера и анимация внутри).
- Вспомогательное: `make_test_bvh.py` (тестовый BVH по спеке), `check_fk.py` (сверка FK Blender с `mp_v2_joints.npz`), `render_full.sh` (полный рендер 4 процессами), `preview_control_frames.jpg` (контрольные кадры t=3,8,13,24,30,40,45,48,51 с, 640x360).

## Как запускать
```
# тестовый кадр (кадр BVH с 0; время печатается как STILL_TIME)
/opt/pv/bin/python -I work/scene/build_scene.py --bvh work/mocap/mocap_final.bvh --still /tmp/f.png --frame-start 1200 [--width 960 --height 540 --samples 3 --quality fast|balanced]
# сохранить сцену
/opt/pv/bin/python -I work/scene/build_scene.py --bvh work/mocap/mocap_final.bvh --save-blend work/scene/pilot.blend
# полный рендер (РЕКОМЕНДУЕТСЯ): 4 параллельных процесса, затем сборка mp4
work/scene/render_full.sh work/mocap/mocap_final.bvh work/scene/character.mp4
#   переменные: SAMPLES (3), QUALITY (fast|balanced), SHARDS (4); доп. аргументы — после OUT
# однопроцессный вариант (с --resume по умолчанию)
/opt/pv/bin/python -I work/scene/build_scene.py --bvh work/mocap/mocap_final.bvh --out work/scene/character.mp4 --samples 3
# частичный/каждый K-й кадр: --frame-start N --frame-end M --frame-step K (видео дублирует кадры до --fps)
```
Прочие флаги: `--engine EEVEE|WORKBENCH|CYCLES`, `--azimuth`, `--focal`, `--cam-height`, `--margin`, `--follow`, `--no-resume`, `--part K/N`, `--assemble-only`.
Прерванный рендер продолжается повторным запуском той же команды.

## Проверка ретаргетинга (реальный BVH `mocap_final.bvh`, 1665 кадров)
- `check_fk.py`: FK в Blender совпадает с `mp_v2_joints.npz` (преобразование (x,y,z)_Blender = (-X, Z, Y)_BVH) с точностью **0.0001 м** по всем 19 суставам. Минимальная высота Toe за всё движение = **-0.0005 м** (стопы стоят на полу).
- Визуально (`preview_control_frames.jpg`): выпады, поднятые над головой руки (45, 51 с), подъём колена (40 с), глубокое приседание (48 с) — без разрывов на суставах, ступни на полу, рамка вмещает всю фигуру во всех контрольных кадрах.
- Сверка с `input/source.mp4` по лево/право: левая рука персонажа = +X BVH = -X Blender (камера видит её справа от персонажа в кадре при фронтальном взгляде). Покадровое визуальное сопоставление с исходным видео оркестратор может сделать по контрольным кадрам; расхождений по сторонам в тестовом движении (подъём левой руки) нет.

## Замеры времени (4 CPU, 15 ГБ, без GPU; EEVEE идёт через Mesa llvmpipe)
Движок `BLENDER_EEVEE` работает без GPU/дисплея только после установки системных `libegl1 libegl-mesa0 libgl1-mesa-dri libglx-mesa0` (`apt-get update && apt-get install -y ...`; в логе остаются безвредные сообщения `EGL_BAD_MATCH`). Без них падает с `Couldn't open libEGL.so.1`. Workbench и Cycles доступны сразу. Первый кадр процесса на 5–10 с медленнее (компиляция шейдеров), здесь он не учитывается.

Секунд на кадр, стационарно, реальный BVH, один процесс (llvmpipe на 4 потоках):

| Режим | 1280x720 | 960x540 |
|---|---|---|
| EEVEE fast (без теней), 1 сэмпл | ~2.3–3.6 (шумно, края ступенчатые) | — |
| EEVEE fast, 2 сэмпла | 3.3 | 3.0 |
| EEVEE fast, 4 сэмпла | 5.3–5.5 | 4.7–4.9 |
| EEVEE balanced (тени), 2 сэмпла | 3.7 | — |
| EEVEE balanced, 4 сэмпла | — | 4.7–4.9 |
| Workbench (studio-свет, 8 AA) | 1.1 | — |
| Cycles CPU 4 сэмпла + denoise | — | 6.4 |

Узкое место EEVEE на llvmpipe — не сэмплы, а фиксированные ~0.8–1.4 с/кадр и пиксельная нагрузка; материалы и число объектов на время почти не влияют. Параллельные процессы заметно выигрывают (каждый с `LP_NUM_THREADS=1`): **4 шарда дают ~2.5–3x** по сравнению с одним процессом. Измеренная эффективная скорость 4 шардов (32 кадра подряд, включая запуск):

| Режим (4 шарда) | эфф. с/кадр | 1665 кадров (55.5 с) |
|---|---|---|
| EEVEE fast, 2 сэмпла, 960x540 | 1.1 | ~31 мин |
| EEVEE fast, 2 сэмпла, 1280x720 | 1.2–1.3 | ~35 мин |
| **EEVEE fast, 3 сэмпла, 1280x720 (по умолчанию в `render_full.sh`)** | ~1.6 (интерполяция) | **~45 мин** |
| EEVEE fast, 4 сэмпла, 1280x720 | 1.9–2.0 | ~55 мин |
| EEVEE balanced (тени), 4 сэмпла, 1280x720 | 3.7 | ~100 мин |
| один процесс, EEVEE fast 2 сэмпла 720p | 3.3 | ~92 мин |
| Workbench, один процесс | 1.1 (параллельно, вероятно ~0.4) | ~30 мин (одним процессом) |

Вариант `--frame-step 2` (15 фактических кадров/с, дублируются до 30) вдвое сокращает время, но движение видно ступенчатым; не рекомендуется. Рендер каждого кадра с 3 сэмплами укладывается в 45 мин, поэтому frame-step не нужен.

## Известные ограничения
- Манекен схематичный (без пальцев и лица); большой палец — декоративный выступ. Жёсткая привязка: на скрутках корпуса сегменты чуть «ступенчатые», без skin-weights.
- В режиме `fast` нет настоящих теней (только пятна под тазом/стопами); окно даёт мягкий свет без светового пятна на полу. `balanced` даёт реальные тени на ~2x дороже.
- Антиалиасинг скромный (EEVEE TAA 3–4 сэмпла); при просмотре 1:1 тонкие рейки на фоне могут слегка мерцать.
- Камера не следует за перемещением вперёд/назад (по глубине), только вбок; рамка подобрана по всему движению, поэтому фигура занимает ~45–60 % высоты кадра.
- Кадрирование рассчитано по суставам (без толщины мешей); запас 10 % перекрывает толщину.
- Система: для EEVEE нужны apt-пакеты Mesa/EGL (см. выше).
